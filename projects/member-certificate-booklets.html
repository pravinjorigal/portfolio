Executive Summary

This project focused on improving the performance of a production API responsible for generating Member Certificate Booklets within a life insurance platform. Performance testing showed that the service consistently exceeded its required response-time SLA, putting a planned production release at risk.

Rather than attempting a large architectural redesign, I investigated the request execution path, identified unnecessary sequential processing, and implemented targeted improvements using asynchronous execution and Redis caching. The resulting solution reduced P90 latency by approximately 75% without changing external API behaviour or downstream integration contracts.

Business Context

Fetching list of Member Certificate Booklets required aggregating information from multiple enterprise systems including member records, policy information, coverage details, and reference data before assembling the final response.

Although each downstream dependency was required for a successful response, many of these operations were independent of one another. Over time, the API had evolved into a mostly sequential workflow, causing overall response time to increase as additional business functionality was introduced.

The production release date had already been committed. Any solution therefore needed to improve performance while minimizing implementation risk and avoiding breaking changes for existing consumers.

Performance Challenge

Initial performance testing showed that the service failed to meet the required two-second SLA.

Measured response times were approximately:

  • Best case: approximately 4 seconds
  • P90 latency: approximately 6 seconds
  • Worst case: approximately 8.5 seconds

Because multiple downstream integrations were mandatory, simply removing service calls was not an option. Likewise, introducing a major architectural rewrite shortly before production would have increased delivery risk and delayed the release.

The challenge therefore became finding measurable performance improvements within the existing architecture while preserving functional behaviour, integration compatibility, and production stability.

My Engineering Ownership

I was responsible for analyzing the performance bottleneck, identifying optimization opportunities, implementing the required backend changes, and validating that each improvement produced measurable results before being considered for production deployment.

Rather than assuming where the latency originated, I approached the problem as a production investigation. Every optimization was driven by measurements, allowing the team to focus engineering effort on the areas that contributed most to overall response time.

My responsibilities included:

  • Analyzing the end-to-end execution flow of the certificate booklets API.
  • Instrumenting request processing to measure the execution time of individual downstream operations.
  • Identifying opportunities for safe parallel execution using CompletableFuture.
  • Introducing Redis caching for stable reference data that was read frequently but changed infrequently.
  • Performing repeated performance testing to validate every optimization before deployment.
  • Supporting production rollout and verifying that functional behaviour remained unchanged after optimization.

Investigation Process

The first objective was understanding exactly where the application spent its time. Rather than optimizing code immediately, I added timestamp-based instrumentation around each major dependency to build an execution timeline for every request.

This investigation showed that several downstream calls executed sequentially even though they were independent once the initial member context had been retrieved. The execution model effectively accumulated the latency of multiple services instead of allowing those operations to overlap.

The investigation followed a straightforward engineering process:

  1. Measure the execution time of every downstream dependency.
  2. Identify redundant work and repeated lookups.
  3. Determine which operations could safely execute concurrently.
  4. Reduce unnecessary database access through caching.
  5. Repeat performance testing after each optimization.
  6. Deploy only after confirming both functional correctness and performance improvements.

Performance Strategy

The optimization strategy focused on reducing unnecessary waiting time rather than rewriting business logic. Existing functionality already satisfied business requirements; the opportunity lay in improving how that work was executed.

Two complementary techniques delivered most of the performance improvement:

  • Executing independent downstream operations concurrently using CompletableFuture.
  • Eliminating repeated retrieval of stable reference data through Redis caching.

Because these optimizations targeted execution behaviour rather than business logic, they significantly improved response time while preserving existing API contracts and downstream integrations.

Key Engineering Decisions

Measure before optimizing

Performance problems are rarely solved effectively through intuition alone. Collecting execution timings first prevented unnecessary code changes and kept the optimization effort focused on the actual bottlenecks rather than perceived ones.

Parallelize only independent work

Not every operation can execute concurrently. The initial member context remained a prerequisite for the request, but once that information became available, several downstream service calls no longer depended on one another.

Using CompletableFuture, these independent operations could execute simultaneously instead of sequentially, reducing overall response time without changing business behaviour.

Cache stable reference data

Some reference information was read frequently but updated infrequently. Rather than repeatedly querying Oracle for identical data, Redis was introduced using a cache-aside approach to reduce unnecessary database access and improve overall request latency.

This optimization also reduced load on downstream infrastructure, providing benefits beyond individual request performance.

Avoid unnecessary architectural change

Although a larger redesign may have offered additional optimization opportunities, it would also have introduced significant delivery risk shortly before the scheduled production release.

The chosen approach deliberately focused on targeted improvements that achieved the required SLA while preserving application stability and minimizing regression risk.

Production Validation

Every optimization was validated through repeated performance testing rather than relying on isolated benchmark runs. Response times were compared before and after each change to ensure measurable improvement while confirming that business functionality remained unchanged.

Following deployment, production behaviour was monitored to verify that the service continued meeting performance expectations under real enterprise workloads. Because the API contract and business logic were preserved, deployment risk remained low despite the significant performance improvement.

Lessons Learned

This project reinforced that effective performance engineering is fundamentally an investigation exercise rather than an optimization exercise. Sustainable improvements come from understanding where time is actually spent, validating assumptions with data, and making targeted changes that address the root cause.

Several engineering principles proved especially valuable throughout this work:

  • Measure system behaviour before proposing solutions.
  • Optimize request flow before optimizing implementation details.
  • Execute work concurrently only when dependencies genuinely allow it.
  • Cache data selectively based on access patterns, data stability, and consistency requirements.
  • Prefer incremental, measurable improvements over high-risk architectural rewrites when working close to production releases.

What I Would Improve Today

If I were solving the same problem today, I would build on the existing solution with additional observability and resilience practices that are now common in modern distributed systems.

  • Use OpenTelemetry distributed tracing to visualize request execution across multiple downstream services.
  • Configure dedicated executors for asynchronous workloads instead of relying on the common thread pool.
  • Introduce Micrometer metrics and latency dashboards to detect performance regressions earlier.
  • Apply circuit breakers, retries, and timeouts around external dependencies where appropriate.
  • Evaluate Java 21 virtual threads for blocking I/O workloads after validating their performance characteristics under production-like load.
  • Automate continuous performance regression testing within the CI/CD pipeline.
