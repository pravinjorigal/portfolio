Java 17 & Spring Boot 3 Migration

Modernized enterprise services from Java 8 and older Spring versions to Java 17 and Spring Boot 3 while preserving existing behaviour and API compatibility.

Why modernization was needed

Several services in a digital insurance platform were running on older technology versions. The move was needed to improve security, maintainability, framework support, and long-term platform health—without interrupting core business operations.

The hard part

This was more than a version change. Libraries, framework APIs, annotations, configuration, and namespaces all had compatibility implications. Third-party dependencies had to be verified, deprecated code replaced, and existing consumers protected from contract changes.

My contribution

I upgraded application components for Java 17, resolved Spring Boot 3 and Jakarta migration issues, fixed dependency incompatibilities, tested migrated functionality, and supported deployment and post-release validation.

How the migration worked

We migrated incrementally rather than rewriting. We first mapped affected components and library compatibility, then updated or replaced unsupported dependencies. The javax.* to jakarta.* transition required more than import changes; framework and annotation behaviour needed validation as well.

Regression testing verified that business behaviour and API contracts remained consistent. The goal was for the technology upgrade to be invisible to end users.

Engineering decisions

  • Java 17: a stable LTS foundation with modern language and security support.
  • Spring Boot 3: alignment with the modern Spring and Jakarta ecosystem.
  • Incremental delivery: smaller changes were easier to test, isolate, and roll out safely.
  • Compatibility first: preserving dependent systems reduced enterprise rollout risk.

Outcome

The work reduced technical debt, improved framework support and dependency hygiene, and created a more sustainable base for future development. It also helped address 100+ vulnerabilities as part of the broader upgrade effort, with zero-regression deployments across environments.

What I would improve today

I would evaluate OpenRewrite for repetitive refactors, add automated compatibility checks to CI/CD, expand integration test coverage before promotion, and use distributed tracing to compare operational behaviour before and after the migration.

Key lesson

Upgrades require the same care as new feature work: understand compatibility boundaries early, move in testable increments, and treat backward compatibility as an engineering requirement.

Recruiter summary
