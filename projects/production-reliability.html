Improving Production Resilience

Investigated intermittent API failures with structured logs and Splunk, isolated a transient downstream timeout pattern, and introduced safe retry behaviour for a customer-facing service.

Incident context

Customer-facing backend services depended on multiple internal systems for policy, member, and account data. When requests failed in production, they affected customer journeys and created work for operational teams.

The problem

An API began failing intermittently while waiting on a downstream enterprise service. The issue could not be reliably reproduced in lower environments, so a production-safe investigation was necessary before any code change was considered.

Investigation and solution

I began with evidence: structured JSON logs in Splunk made it possible to trace affected requests and compare successful versus failed paths. The failures consistently occurred when the dependency experienced temporary response delays.

After validating that these were transient—not permanent—failures, I implemented a retry strategy with Resilience4j. The configuration was tested to improve recovery while avoiding duplicate processing and unnecessary load on the dependency, then monitored after release.

Engineering decisions

  • Structured logging: searchable fields, timestamps, and request context shortened root-cause analysis.
  • Retry: gave transient communication errors a controlled recovery path.
  • No circuit breaker initially: retry addressed the observed failure pattern with lower delivery complexity; broader protection was reserved for future scale needs.

Outcome

RCA

moved from guesswork to evidence-led investigation
Automatic recovery for transient failures

The service became more resilient to temporary downstream issues, investigations became faster, and the team had a clearer operational pattern for handling similar failures.

What I would improve today

I would complement retry with circuit breakers and bulkheads, propagate correlation IDs across services, add OpenTelemetry tracing and SLO dashboards, and configure automated alerts for failure and latency trends.

Key lesson

Observability is an engineering capability. A small, measured resilience change can be more valuable than a broad architecture rewrite when it is grounded in production evidence.

Recruiter summary

Used structured logs and Splunk to root-cause an intermittent production timeout, then shipped a targeted Resilience4j retry strategy—turning a hard-to-reproduce incident into an automatically recovering, well-understood failure mode.
