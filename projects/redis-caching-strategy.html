Executive Summary

As part of a broader performance improvement initiative, I designed and implemented a Redis-based caching strategy for frequently accessed reference data within an enterprise insurance platform. Rather than caching everything, the solution focused on identifying data that changed infrequently but was read on almost every request.

The implementation used a cache-aside pattern with carefully selected, dataset-specific expiration policies. This reduced redundant Oracle database reads, lowered request latency, and supported overall platform performance without compromising data consistency or changing existing API contracts.

Business Context

Several high-traffic APIs repeatedly retrieved the same reference information, including product configuration, lookup tables, and plan metadata. Although this information changed infrequently, every request still required database queries, increasing latency and placing avoidable load on Oracle.

Performance analysis showed that these repeated reads were contributing to higher response times across the platform. Improving efficiency required reducing unnecessary database access while ensuring that business-critical data remained accurate and trustworthy.

Caching Challenge

Introducing Redis was not the difficult part. The engineering challenge was determining what should be cached, how long it could safely remain in cache, and when data should be refreshed without affecting business correctness.

Oracle remained the system of record throughout the solution. The cache was introduced solely to optimize read performance, meaning stale or inconsistent data could never become an acceptable trade-off.

The solution therefore needed to balance two competing objectives:

  • Reduce repeated Oracle database access for frequently requested data.
  • Maintain predictable data freshness for business-critical information.
  • Avoid introducing unnecessary architectural complexity.
  • Improve performance without changing existing client-facing API behaviour.

My Engineering Ownership

My responsibility was to identify where caching would provide measurable value without introducing data consistency risks. This involved analyzing request patterns, evaluating data change frequency, implementing the caching layer, tuning expiration policies, validating correctness through testing, and monitoring behaviour after production deployment.

Rather than treating Redis as a universal solution, I evaluated individual datasets based on their read frequency, update frequency, and business impact if stale data were temporarily served. Only datasets that satisfied those criteria were selected for caching.

My responsibilities included:

  • Analyzing request flows to identify repeated Oracle database access.
  • Selecting reference datasets suitable for caching.
  • Designing and implementing a cache-aside strategy using Redis.
  • Defining dataset-specific cache expiration policies.
  • Performing performance and regression testing before release.
  • Monitoring cache behaviour and validating production performance after rollout.

Caching Strategy

The solution adopted the cache-aside pattern. Each request first attempted to retrieve data from Redis. If the requested entry existed, it could be returned immediately without querying Oracle. If the entry was missing or had expired, the service retrieved the data from Oracle, populated Redis, and returned the fresh result to the client.

This approach kept Oracle as the single source of truth while allowing the cache to optimize repeated read operations. Because writes continued to flow directly to Oracle, the solution introduced minimal change to the existing application architecture.

Instead of applying one global expiration policy, cache lifetimes were tuned for individual datasets based on how frequently the underlying business data actually changed.

Key Engineering Decisions

Cache-aside instead of write-through

The application workload was heavily read-oriented. Cache-aside minimized implementation complexity by leaving the write path unchanged while still eliminating most repeated database reads. This reduced deployment risk and kept business logic straightforward.

Dataset-specific TTL values

Different datasets changed at different rates. Applying a single expiration period across all cached data would either refresh stable datasets unnecessarily or retain changing data longer than desired. Individual TTLs allowed each dataset to balance performance with freshness.

Redis instead of local in-memory caching

The platform operated multiple instances of the application. A shared Redis cache ensured all instances observed consistent cached data while avoiding duplicate memory usage and inconsistent cache contents across servers.

Incremental adoption

Rather than caching every database query immediately, caching was introduced only for carefully selected reference datasets. This reduced operational risk and made performance improvements easier to measure and validate.

Data Consistency Considerations

Improving performance was only one objective. Preserving business correctness was equally important. Oracle remained the authoritative source of data, and Redis functioned purely as a temporary optimization layer.

Before introducing caching, each dataset was evaluated using questions such as:

  • How frequently does this data change?
  • Would a short delay before refresh create any business impact?
  • Does serving slightly older data affect customer outcomes?
  • Can the data always be reloaded safely from Oracle?

Only datasets with low change frequency and minimal business risk were cached. This selective approach improved performance while maintaining confidence in the correctness of the information returned to client applications.

Production Validation

Following deployment, application logs and Splunk dashboards were used to verify that cache behaviour matched expectations. Oracle query volume, cache hit patterns, response latency, and overall application performance were monitored to confirm that the implementation delivered measurable improvements.

During validation, one dataset demonstrated that its original expiration period was longer than necessary for its update frequency. Rather than removing caching, the TTL for that dataset was reduced, reinforcing the importance of treating cache configuration as an operational tuning exercise instead of a one-time implementation task.

Results

Lower Load

Reduced unnecessary Oracle queries
Frequently requested reference data was served directly from Redis, significantly reducing repeated database access for high-volume APIs.


Faster

Improved application responsiveness
Eliminating repeated database lookups reduced request latency and contributed to the platform-wide performance improvements delivered during the broader optimization initiative.


Reliable

Maintained data consistency
Oracle remained the system of record while carefully selected TTL values ensured cached data stayed operationally accurate without changing client-facing API behaviour.

The caching strategy became an important component of the platform's overall performance improvements. By reducing avoidable database work instead of adding new infrastructure or redesigning application architecture, the solution helped improve scalability while preserving operational simplicity.

Lessons Learned

This project reinforced that effective caching is fundamentally an engineering trade-off rather than a technology decision. Improving performance is valuable only when correctness, maintainability, and operational visibility are preserved.

Several principles proved especially important:

  • Cache only data with predictable update characteristics.
  • Keep the primary database as the authoritative source of truth.
  • Treat TTL values as business decisions rather than arbitrary configuration.
  • Measure cache effectiveness using production metrics instead of assumptions.
  • Introduce caching incrementally so behaviour can be validated safely.

What I Would Improve Today

If implementing this solution today, I would extend the caching strategy with additional observability and more sophisticated invalidation mechanisms while keeping the same cache-aside architecture.

  • Expose cache hit, miss, and eviction metrics using Micrometer and Prometheus.
  • Evaluate event-driven cache invalidation for datasets that change more frequently.
  • Protect against cache stampedes using request coalescing or distributed locking for hot keys.
  • Introduce a lightweight in-memory L1 cache for extremely hot reference data where appropriate.
  • Perform periodic cache effectiveness reviews to adjust TTL values as business usage evolves.
  • Create dashboards correlating cache hit ratio, Oracle query volume, and API latency to simplify operational tuning.

Recruiter Summary

The solution reduced unnecessary database load, contributed to platform-wide latency improvements, and demonstrated production-oriented engineering judgment around caching strategy, scalability, and operational reliability.
