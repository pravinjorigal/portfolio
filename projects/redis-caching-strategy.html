Redis Caching Strategy

Designed a cache-aside strategy for slow-changing reference data behind a high-traffic insurance platform, cutting redundant database round-trips without introducing staleness risk.

Role · Backend EngineerDomain · Life insuranceProduction · YesConfidential · Generic architectureFocus · Caching & data consistency

At a glance

Pattern
Cache-aside with time-based expiry
Stack
Java 17, Spring Boot, Redis, Oracle, Splunk
Load
Platform serving ~50K–100K requests/day

Business context

Several APIs on the platform repeatedly read the same low-change reference data—plan details, product configuration, lookup tables—on nearly every request. That data changed infrequently but was queried constantly, and it was one of the contributors to a production SLA breach investigated as part of the platform's broader performance work.

Constraints

The data source of truth stayed Oracle; the cache could not become an alternate source of truth. Any staleness window had to be short enough to be operationally invisible, and the change had to ship without altering API response contracts.

My role

I identified which reference datasets were safe to cache by tracing request timing and change frequency, then implemented and tuned the caching layer, verifying correctness through repeated performance and regression testing before release.

Solution

I introduced a cache-aside pattern: a service first checks Redis for a key, and on a miss reads Oracle, populates the cache, and returns the result. Keys were scoped by entity and version to avoid collisions, and expiry was set per dataset based on how often each one actually changed, rather than a single global TTL.

Engineering decisions

  • Cache-aside over write-through: the read pattern was highly skewed toward reads, and cache-aside kept the write path untouched and low-risk.
  • Per-dataset TTLs: a single blanket expiry either invalidated too eagerly or held stale data too long; tuning per dataset matched actual change frequency.
  • Redis over local in-memory cache: the platform ran multiple service instances, and a shared cache avoided per-instance inconsistency and duplicated memory cost.
  • No proactive cache warming initially: the miss penalty was small and infrequent enough that added warming complexity wasn't justified.

Challenges

  • Choosing TTLs that were short enough to avoid visible staleness but long enough to meaningfully reduce load.
  • Avoiding key collisions across similarly named entities from different downstream systems.
  • Keeping cache population out of the critical path when a key had already expired under load.

Business impact

Caching removed one of the largest sources of repeated, avoidable database and downstream work, and was a direct contributor to the platform's P90 latency dropping from roughly six seconds to about 1.5 seconds—helping the service meet its SLA without a broader architecture change.

Production support story

After rollout, Splunk dashboards were used to watch cache hit rates and confirm Oracle read volume actually dropped as expected. When one dataset's TTL was initially set too long, a delayed-looking update was reported by QA; the fix was a shorter, dataset-specific TTL rather than removing caching altogether.

Lessons learned

Caching is a data-freshness decision as much as a performance one. The right question isn't "should we cache this," but "how stale can this be before anyone notices or cares"—and that answer is different for every dataset.

What I would improve today

I would add cache-hit/miss metrics per key pattern via Micrometer, evaluate event-driven invalidation for the datasets that do change, and consider a short local L1 cache in front of Redis for the very hottest keys.

Recruiter summary

Designed a per-dataset cache-aside strategy in Redis for a high-traffic insurance platform, removing redundant database reads and contributing directly to a ~75% P90 latency improvement without risking data staleness.
