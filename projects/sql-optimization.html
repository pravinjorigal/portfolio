SQL Optimization

Rewrote slow Oracle queries and indexing behind a banking search and export feature, turning multi-second table scans into fast, predictable lookups.

Query design & indexing

Business context

A banking onboarding platform exposed an advanced search feature and a bulk Excel export used by internal operations teams to pull large, filtered customer datasets. As data volume grew, both features slowed down, and the export in particular risked timing out on large result sets.

Constraints

The schema was shared with several other services and couldn't be redesigned outright. Any query changes had to preserve existing filter and sort behavior exactly, and changes had to roll out through the platform's standard release process without downtime.

My contribution

I profiled the slow queries, redesigned indexing and query structure for the search path, and built reusable Oracle database functions so multiple call sites could share the same optimized logic instead of duplicating ad-hoc SQL.

Solution

Working with MyBatis, I replaced several queries that scanned wide tables with versions that used composite indexes matching the actual filter and sort combinations the UI allowed. For the export feature, I moved from row-by-row fetching to batched retrieval, so large datasets could be streamed to Excel without holding the entire result set in memory.

Engineering decisions

  • Composite indexes over single-column indexes: real queries filtered and sorted on multiple columns together, so indexes were designed around actual query shapes, not individual columns in isolation.
  • Reusable database functions: centralizing shared logic in Oracle functions reduced duplicated, slightly-inconsistent SQL across services.
  • Batched export: streaming results in batches kept memory use predictable regardless of export size.
  • No schema migration: indexing and query changes delivered most of the benefit with far less risk than a schema redesign under a shared-schema constraint.

Challenges

  • Identifying which of several similar-looking queries were actually responsible for the worst-case slowdowns.
  • Adding indexes without degrading write performance on tables used by other services.
  • Validating that optimized queries returned identical results to the originals across edge-case filters.

Business impact

Search responses became fast enough for interactive use, and the export feature stopped being a timeout risk for large pulls—reducing support escalations from operations teams and removing a recurring source of manual workarounds.

Production support story

Before the change, operations occasionally reported exports "hanging" on large date ranges; investigation traced this to full table scans rather than a code defect. After the fix, the same date ranges completed reliably, and the underlying indexing pattern was reused for a later reporting feature with the same access pattern.

Lessons learned

Most SQL performance problems are query-shape problems, not "the database is slow." Designing indexes around how the application actually filters and sorts—rather than one index per column—was the change that mattered most.

What I would improve today

I would add query plan monitoring in lower environments before release, load-test the export path with representative data volumes, and consider read replicas for reporting-style queries to isolate them from transactional traffic.

Recruiter summary

Diagnosed and fixed slow Oracle queries behind a banking search and export feature through composite indexing and batched retrieval, removing a recurring operational pain point without a schema redesign.
